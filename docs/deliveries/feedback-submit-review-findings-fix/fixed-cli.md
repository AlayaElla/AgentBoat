# 验收附件命令入口修复

本机 Orca 1.4.280 的只读核对显示，AgentBoat v0.1.55 开发候选正在运行且授权有效。`agentboat-current` 仍是指向正式 v0.1.52 的 Windows 目录联接。v0.1.52 的 `projects` 可以连接新 worker，`feedback-file` 则在旧客户端解析阶段报通用用法。

新验收和决定的附件通知直接给出 `node <脚本> feedback-file ...` 命令，注明由项目主会话在自己的 Orca 会话执行。每项反馈的首个附件可直接复制命令，其余附件换用该项下对应的编号。决定附件继续带 `--decision`。通知使用当前 worker 随包的客户端，只有在正式目录联接经只读检查指向该 worker 的同一版本目录时才显示固定入口。候选模式下用本次加载包的绝对路径。入口校验失败时，仍可在任务详情的记录中查看附件。

查询沿用现有本机请求及绑定校验。客户端从自己的 Orca 会话读当前 Run，worker 核对项目主会话、任务、事项、版本和附件编号。用户级 hooks 继续经正式安装入口。附件通知生成期间不更新目录联接、hooks 或 Orca 授权。

## 本机应用

- **正式版**。含本修复的 AgentBoat 版本可用后，在对应本机 Orca 配置运行 `orca plugin update alayaella.agentboat --environment local`。如 Orca 要求批准，先核对来源、版本和批准回执中的权限。若已有开发覆盖，切回正式版需经授权卸载对应候选目录。启动工作间后，核对 `orca plugin list --environment local --json` 中 `alayaella.agentboat` 的运行状态和 `isDev: false`，并确认 `agentboat-current` 已指向该正式版本。固定到某个提交的安装不会随更新向前移动，需要通过原可信安装来源明确选择含修复的版本。
- **开发候选**。在本机按现有发布产物构建流程生成独立候选，用 `orca plugin inspect <候选目录> --json` 核对身份和内容，再用 `orca plugin dev load <候选目录> --environment local --json`，按 Orca 回执批准该包的现有权限。确认 `isDev: true` 且状态为 `running` 后，在项目主会话执行新通知中的完整命令。开发目录改名、替换或卸载后，如需处理旧通知，沿用旧通知中的项目、任务、事项、版本及附件编号，脚本路径改为当前已核验且已加载的包，或在任务详情的记录中打开附件。已经送出的通知保留原文。

## 验证

- 类型检查和 `git diff --check` 通过。固定入口和 CLI 鉴权共 8 项通过。原决定与验收的附件重试、重启和版本定位回归通过。
- 用临时 Orca 配置运行打包布局中的当前 worker 和真实本机请求桥。将本机 v0.1.52 `client.mjs` 的只读副本放在隔离的固定入口，复现 `projects` 成功而 `feedback-file` 报通用用法。由实际 `project.feedback` 处理器生成验收通知，从通知复制命令经 PowerShell 执行，回执路径的文件字节与上传一致。相同命令由其他会话执行时，worker 拒绝查询。Orca 的 Run 和项目存储由隔离宿主提供。
- 隔离正式版启动刷新将固定入口切到当前版本。由同一通知链路生成的固定入口命令实际取回文件。另验证指向无关目录的联接会保持原目标，目录中带写入标记的脚本没有执行。候选设置的既有回归通过，临时 hooks 与正式入口归属检查照常生效。
- 首次开发测试中的正式刷新子步骤沿用了本机用户目录，读到了归属另一配置的 hooks，并短暂取得了本机设置锁。该次未匹配这些文件的写入归属，锁已释放。随后将该步骤移入临时用户目录，以上通过结果来自修正后的隔离测试。

本机 v0.1.55 和 v0.1.52 状态核对为只读。正式覆盖切换、真实项目中生成通知和读取附件、发布均未执行。改动在 `store.ts` 的反馈通知生成处及 CLI 路径解析，`worker.ts` 无差异。`coordinator.test.ts` 只调整附件回归对通知文案的断言。
