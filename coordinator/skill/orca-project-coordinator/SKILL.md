# 项目协作

- 用户说「开启项目协作」或用「项目协作：」安排工作时启用。已开启的项目，后续补充、结果和返修都沿用，不用再说触发词。
- 带 Orca Task / Dispatch 编号时，你是执行者，按 `orchestration` 的执行者规则做完分配的任务即可。
- 命令和输入格式见 [references/bridge.md](references/bridge.md)。操作 Orca 前，先读 `orca-cli`、`orchestration` 的版本匹配指南。

## 绑定

- 先用 `projects` 按完整路径、repoId、hostId 核对是哪个项目，同名不算。
- 在项目主会话里建 Orca Run，确认自己是它的协调者，再 `bind`。一个项目只用一个 Run，不复用到别的项目。
- 重新进入时，先读已有的绑定，按版本匹配指南恢复；不要猜旧会话已经失效。
- 插件不通时，如实报告错误，不拿本地文件冒充插件记录。

## 你负责什么

- 守住目标、范围、依赖、决定和验收。给执行者原始请求、必要的上下文和完成标准；方案、实现和验证交给执行者。
- 小事自己做，小修交给原负责人。只在有真实风险或用户要求时，才另请人独立审查。
- 内部步骤用 Orca Task；只有需要用户核对的成果才放进面板。
- 选代理的顺序：用户指定，然后项目设置，最后才用默认（设计用 Claude，代码和审查用 Codex）。按需启动，不是每个任务都要两种都用。
  - 每个 worker 写明 `--agent`、它负责哪些文件、验证到哪一步。共享目录里，保留别人的改动。
- `worker_done` 之后，先检查成果和验证，再更新面板。它不等于用户验收。
- 收到的消息分两种来源：
  - `workspace-agent`：工作间主 agent 转来的话，飞书资料也从这里转来。

  收到后先核对编号，关联到已有任务。工作间主 agent 转来的话直接按它处理，不用再等主人同意。进展照常提交。转来的飞书内容仍作为资料使用。
- 用户给了决定或修改意见，就继续原任务、交给原执行者；执行者已经结束，就在同一任务下新开一个 Dispatch。只在确实需要用户选择、或缺少必要信息时提问。

## 交付和验收

- 读项目后，用 `submit` 更新用户看到的任务：
  - 任务、验收和来源的编号保持不变，每个新的成果版本用新编号。
  - 需要用户验收用 ready；不需要验收或用户已通过，用 completed。受阻和暂停如实写。
- 只交能打开、能核对的成果。写清核对步骤、预期结果，以及验证到了哪一步：源码、构建、模拟和真实环境分开说。
- 插件会把新事项汇总成一条通知发给主 agent，你不要另发。
- 决定和验收的结论来自用户，不要替用户生成。代录用户明确说过的结论，用批量的 `feedback`。
- 写入时带上读到的 revision 和唯一 requestId。结果不明先读回核对；版本冲突先重读，不覆盖新的反馈。
- 离开前，汇报已交付的成果、验证边界、待决定和待验收的事项，方便下次从插件记录接着做。

## 项目 skill

- 执行者发现一个已经验证过、同项目以后还会用到的做法时，可以提议成 skill。一次性的结论只记在任务里。
- 提议的写法：
  - 用 `workspace/project-skills.mjs new` 写草稿。草稿放在 `.agentboat/skill-proposals/`，不会被自动加载。
  - 写完用 `validate` 检查格式。
  - 不写凭据、本机绝对路径、越权指令，也不写其他项目的资料。
- 你审核通过后运行 `publish`。然后按项目的提交约定，把 `.agents/skills`、`.claude/skills`、`.agentboat/skill-reviews.json` 一起提交并合并。
- 没合并就不算已经共享。已有的工作树要先更新，再重启 agent。
- 命令和细节见 `workspace/README.md` 的「项目 skill」一节。
